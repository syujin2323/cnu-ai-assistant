## 2026-10-11 사캠 연동 방식

- 결정: 사캠 연결 방식은 둘이고, PC 브라우저 확장으로 연결하는 'PC 연결'이 기본이며 R0에는 이것만 있다. 폰 앱 안에서 사캠 세션을 오래 유지하는 것은 현실적으로 어렵기 때문이다. 확장은 로그인하지 않고, 사용자가 PC에서 사캠 페이지를 열 때 브라우저가 이미 가진 사캠 세션으로 할 일을 읽어, 폰만 풀 수 있게 암호화해 서버를 거쳐 폰으로 보낸다. PC 연결의 약속은 "PC에서 사캠에 접속할 때마다 최신"이다. PC가 없거나 PC에서 사캠을 쓰지 않는 학생은 R0에서 할 일을 직접 입력하고, R1부터 보조 방식인 '폰 직접 연결'을 쓴다. 폰 직접 연결의 로그인은 사용자가 앱 안 WebView의 공식 화면에서 직접 하고, 앱은 비밀번호를 다루지 않으며 자동 재로그인을 하지 않는다. 쿠키는 OS 보안 저장소(쿠키 금고)에 두고, 응답 판별기, 세션 복원, 한 번에 하나만 도는 동기화로 세션을 최대한 오래 쓴다. 폰 직접 연결의 약속은 "앱을 열면 최신"이고 백그라운드 갱신은 덤이다. R1부터 온보딩과 설정에서 두 방식을 고르게 하고 PC 연결을 먼저 권한다. 원격 스위치로 앱과 확장의 사캠 연동을 끌 수 있게 한다. 동작 규칙은 [lms.md](lms.md)에 있다.
- 이유: 사캠에는 로그인 상태 유지 기능이 없고 세션 쿠키에 만료 시각이 없다. 계정당 세션이 하나뿐이라는 관찰이 있어 앱의 자동 로그인이 PC 영상강의 세션을 끊을 수 있다. 학외 포털 로그인은 2차 인증이 필수다. 폰 앱이 세션을 지키려 애쓰는 것보다, 영상강의 때문에 이미 로그인해 두는 PC 브라우저의 세션을 쓰는 쪽이 확실하다. 폰 직접 연결을 R1로 미루면 R0에 연결 방식이 하나뿐이라 폰 세션 실험(T1–T11)과 iOS 쿠키 브리지 없이 하루 루프를 먼저 완성할 수 있다.
- 다른 후보: 폰 직접 연결을 기본으로 두고 PC 연결은 R1에 보조로(폰 세션이 자주 끊겨 사용자가 로그인 화면을 자주 본다), 폰 직접 연결을 R0에 보조로 함께 두기(폰 세션 실험과 iOS 쿠키 브리지까지 R0에 들어가 범위가 커진다), 비밀번호를 폰에 저장해 자동 재로그인(PC 세션 충돌, 유출 책임), 서버 대리 로그인(유출 책임, 학교 차단 위험).

## 2026-10-11 AI 사용 방식

- 결정: 앱은 LLM을 직접 부르지 않고 Functions의 AI 게이트웨이를 거친다. 게이트웨이 안의 제공사 어댑터 뒤에 모델을 두어, 모델을 바꿔도 앱은 바뀌지 않는다. 모델은 아직 정하지 않았다. 후보는 Claude Haiku 5.5, Gemini Flash-Lite, GPT 소형 모델이고, 한국어 평가 세트 결과(날짜·시각 정확도, 의도 분류, 규칙 정확도, 응답 시간, 비용)로 정한다. 출력은 `schema/`의 JSON Schema로 강제하고, 날짜·시각·배치 계산은 코드가 한다. 말로 정하는 배치 규칙('내 규칙')도 LLM은 문장을 정해진 규칙 JSON으로 바꾸기만 하고 적용은 폰의 코드가 한다. 브리핑에 보내는 제목은 자리표시자로 가린다. 설치당 하루 30회나 서비스 전체 하루 1,000회를 넘거나 AI가 실패하면 템플릿과 직접 입력으로 바꾼다. 한국어 평가 세트(100문장 이상)에서 날짜·시각 정확도 95% 이상, 의도 분류 97% 이상, 규칙 정확도 95% 이상, 응답 p95 2초 이내를 맞춘 뒤 실제 사용자에게 연다. [architecture.md](architecture.md)의 제공사 호출 규칙은 후보 Claude Haiku 5.5 기준의 임시 규칙이다.
- 이유: 키를 숨기고 남용과 비용을 서버에서 막는다. 같은 입력에 같은 계획이 나와야 사용자가 믿고 테스트할 수 있다. 해외 AI로 가는 개인 데이터를 줄인다. 모델은 평가 결과를 보고 정해야 하므로 지금 고정하지 않는다.

## 2026-10-11 출시 단계

- 결정: R0는 Android(APK)와 iOS(기기 등록 배포)를 Firebase App Distribution으로 내고, PC 확장은 빌드 결과물(`extension/dist`)을 zip으로 묶어 팀 비공개 채널로 주고 브라우저 개발자 모드로 설치하게 한다. R1은 Android(Play 비공개 테스트), iOS(TestFlight), PC 확장(Chrome 웹 스토어 미등록)으로, R2는 Play 스토어, App Store, Chrome 웹 스토어 공개로 낸다. R0에는 PC 확장(R0의 유일한 사캠 연결 방식)과 중계 서버, 폰의 PC 연결 화면, 온보딩, 시간표·고정 일정, 홈, 일간·월간 캘린더, 과제 목록·상세, 자동 배치와 확정·블록 근거, 내 규칙, 리마인더, 아침 브리핑(어제 못 한 일 포함), 말로 일정 추가, 데모 모드, 원격 스위치, 핵심 모션 네 가지(rise, pop, 누름 press, 하단 탭 navDrop·navIconPop), 개인정보 처리방침 초안이 들어간다. R0 작업 순서는 세션 실험 T13 → PC 확장 → 중계 서버 → 폰의 PC 연결 화면·수신이다. 폰 직접 연결(보조)과 새 할 일 FCM 푸시는 R1이다. 학교 확인을 받기 전에는 스토어 빌드에서 사캠 연동을 뺀다. App Check는 R0에서 기록만 하고 R1부터 강제한다.
- 이유: 하루 루프가 실제 계정으로 도는 것을 먼저 만든다. PC 연결이 기본이므로 R0부터 확장이 있어야 루프가 돌고, 확장은 조회·암호화·올리기만 하고 해석은 폰이 하므로 R0에 넣어도 코드가 작다. Chrome 웹 스토어 심사를 기다리지 않도록 R0는 수동 설치로 낸다. R0에는 Android에서만 되는 기능이 없어 iOS를 함께 내도 기능은 같고, iPhone 사용자(20대 절반 이상)를 처음부터 시험할 수 있다. 알림 감지 권한은 APK 직접 설치에서 '제한된 설정'으로 막히고, App Check의 Play Integrity 제공자는 기본 설정에서 Play 인식(PLAY_RECOGNIZED) 라벨을 요구해 Play 밖에서 설치한 APK에는 토큰을 주지 않으므로, R1부터 Android는 Play 비공개 테스트로 배포한다.
- 다른 후보: PC 확장을 R1로 미루기(기본 연결 방식이 R0에 없게 됨), R0를 Android 전용으로 내고 iOS는 R1부터(iPhone 사용자를 늦게 시험함), App Check 고급 설정에서 Play 인식 라벨 요구를 끄고 R0 APK부터 강제(Play 밖 설치를 모두 통과시켜 무결성 검사의 의미가 줄어듦).

GitHub 비밀값 푸시 차단을 켜고 `pr-check`에 쿠키 헤더와 토큰 모양을 찾는 검사를 더한다. AI 기능은 처음 쓸 때 보내는 내용을 보여 주고 동의를 받는다. 앱, 확장, 스토어, 로그인 화면에 "충남대 비공식 앱"을 표시한다.
- 이유: 공개 레포에 수집 도구와 개인정보가 남지 않게 한다. Apple 심사 지침 5.1.2(i)와 Play 사용자 데이터 정책이 외부 AI와 데이터를 나누기 전 동의를 요구하고, 개인정보 보호법이 국외 이전 고지를 요구한다.

## 2026-10-11 PC 브라우저 확장

- 결정: PC 브라우저 확장을 R0에 기본 연결 방식으로 낸다(Chrome·Edge·Whale). 확장 이름은 앱 이름과 함께 정하고, 그전까지 manifest의 이름은 'PC 연결'이다. 확장은 로그인하지 않고 브라우저의 사캠 세션으로 할 일을 읽어, 확장이 만든 키로 암호화해 서버를 거쳐 폰으로 보낸다. 조회는 주기 알람 없이 사용자가 사캠 페이지를 열 때 하고(직전 조회 뒤 일정 시간이 지났을 때만, 하루 횟수 상한 안에서), 과목 전환이 필요한 상세 조회는 사용자가 보는 사캠 화면이 바뀌지 않도록 마지막 사캠 탭을 닫을 때 한다. 간격과 횟수는 [lms.md](lms.md)의 호출 예산을 따른다. 확장 권한은 `storage`와 사캠·앱 서버 호스트 권한뿐이다. 키는 QR로 폰에만 넘기고, 서버는 암호문을 7일까지만 둔다. 사캠 응답을 폰 DB용으로 해석하는 코드는 폰의 Dart(`app/lib/lms/`)에만 둔다. 확장은 응답 원문을 그대로 암호화해 올리되, 새 할 일·마감 변경 비교, 다른 계정 판별, 로그인 페이지 판별에 필요한 값(항목 ID, 마감, 과목 ID, 로그인 페이지 표식, JSON 인증 오류 표식)만 서버가 내려주는 확장 설정의 필드 경로와 표식으로 읽는다. 그 밖의 해석은 하지 않는다. R1부터 PC 연결을 켜면 폰 직접 연결은 기본으로 끈다. 새 할 일 FCM 푸시는 R1에 더하고, R0에서 서버는 확장이 보낸 알림 표시를 저장만 한다.
- 이유: 폰 앱 안에서 사캠 세션을 오래 유지하는 것은 현실적으로 어렵다. 폰 세션은 학교 서버 사정으로 끊길 수 있고, iPhone은 앱을 끄면 세션 쿠키가 지워진다. PC로 강의를 듣는 학생은 브라우저가 이미 로그인해 있어서, 그 세션을 쓰면 새 로그인 없이 데이터를 받고 계정당 세션 하나를 두고 다투지 않는다. 사용자가 사캠을 쓰는 동안에만 조회하면 세션이 살아 있을 때만 요청하고, 사캠을 쓰지 않는 시간에는 학교 서버를 부르지 않는다. 대신 PC에서 사캠을 한동안 열지 않으면 갱신되지 않으므로 폰에 마지막 확인 시각을 늘 보여 준다.
- 다른 후보: 폰 직접 연결만 두기(세션이 끊길 때 대안이 없음), PC 확장을 R1 보조로 두기(R0 내내 세션 끊김을 사용자가 감당함), 브라우저가 켜져 있는 동안 60분마다 조회(사캠을 쓰지 않을 때도 학교 서버를 부르고, 세션이 끊긴 뒤에도 요청이 감), 서버가 PC 세션을 받아 조회(서버에 세션이 모임), Safari·Firefox 확장(쓰는 학생이 적고 따로 배포해야 함).

## 2026-10-12 하루 루프와 배치 엔진

- 결정: 빈 시간 계산과 배치는 AI가 아니라 `app/lib/domain/`의 결정적 Dart 코드가 하고 단위 테스트로 지킨다. 하루 경계·하루 창·브리핑 시각·수업 버퍼·식사 보호 같은 시각·분 기본값은 팀이 정한 값이 아니라 `domain/defaults.dart`의 임시값이며, 사용자 테스트 뒤 정한다(값은 [architecture.md](architecture.md)에 있다). 사용자는 '내 규칙'(2026-10-13)으로 자기 값을 정하고 배치 엔진은 그 규칙을 따른다. 할 일마다 여유도(마감 전 빈 시간의 합 − 남은 작업 시간)를 계산해 여유도가 작은 순으로 넣고, 자리 점수는 길이 맞음·선호 시간대·관련 수업과의 거리·조각남 정도로 매긴다. 큰 일은 조각으로 나누고 짧은 빈 구간에는 큰 과제를 넣지 않는다(조각 길이의 기준값은 임시값). 마감 뒤나 영상 공개 전에는 배치하지 않는다. 계산할 때마다 마감이 가까운 할 일(기간은 임시값)을 모두 빈 시간에 '제안' 블록으로 배치하고, 사용자가 브리핑이나 홈에서 '모두 확정'하거나 블록마다 확정·옮기기·지우기를 한다. 옮긴 블록은 그 시간으로 확정된다. 확정한 블록은 자동으로 옮기지 않고, 재계산은 제안 블록만 다시 만든다. 블록마다 근거(마감까지 남은 기간, 빈 시간 길이, 급한 순번, 고른 이유 한 줄)를 저장해 블록을 누르면 보여 주고, 과제 상세에서는 블록을 옮길 다른 시간 3개를 이유와 함께 보여 준다. 마감 전 빈 시간의 합이 남은 작업보다 적으면 배치 대신 '시간 부족'을 알린다. 리마인더는 마감 며칠 전과 당일, 확정 블록 시작 전에 보내고 완료하면 남은 알림을 취소한다. 알림에는 하루 상한과 조용한 시간을 두되 그 값은 임시값이다. 브리핑에는 '어제 못 한 일' 카드(전날 놓친 확정 블록과 다시 놓인 시각)를 두고, 미완료마다 따로 알림을 보내지 않는다. 브리핑의 사실 초안은 앱이 백그라운드로 갈 때마다 코드가 다시 만들고 브리핑 알림을 폰에서 미리 예약하며, AI 문장은 전날 저녁 이후 처음 백그라운드로 갈 때 하루 한 번만 만든다(기준 시각은 임시값). 데모 모드는 샘플 학생의 하루로 모든 R0 화면이 돌고 실제 데이터와 섞이지 않는다.
- 이유: 같은 입력에 같은 계획이 나와야 사용자가 믿고 테스트할 수 있다. 기본값은 코드 한 곳(`domain/defaults.dart`)에만 두어 화면과 테스트마다 다른 숫자가 들어가지 않게 하고, 값 자체는 사용자 테스트 뒤 정한다. 자동 배치는 팀의 처음 기능 명세가 정한 방식이고, 확정은 사용자가 해 모르는 사이 일정이 바뀌지 않게 한다. 근거를 보여 주면 제안을 믿고 확정하기 쉽다.
- 다른 후보: LLM이 배치(결정적이지 않고 호출 비용이 든다), 점수 없이 가장 긴 빈 구간만 추천(선호 시간대와 수업 거리를 반영하지 못한다), 할 일마다 자리 3개를 보여 주고 사용자가 고르기(할 일이 많으면 손이 많이 간다), 자동 배치를 바로 확정(사용자가 모르는 사이 일정이 바뀐다), 근거를 늘 블록 아래에 표시(홈 카드가 길어진다).

## 2026-10-13 처음 기능 명세와 맞추기

- 결정: 팀의 처음 기능 명세와 지금 설계를 비교해 아래처럼 정했다.
  - 구조: 처음 명세의 서버 agent(스케줄링·브리핑·알림) 대신 지금의 폰 중심 구조를 유지한다. 사용자 데이터, 배치, 알림 예약, 내 규칙은 폰에 두고, 서버는 AI 게이트웨이·공개 데이터·암호문 중계만 맡으며 계정을 두지 않는다. 처음 명세의 agent 역할은 폰의 결정적 코드(배치 엔진, 알림 예약, 브리핑 사실 초안)와 게이트웨이의 LLM 호출(일정 문장 해석, 규칙 문장 해석, 브리핑 문장)이 나눠 맡는다. 폰 DB는 지금처럼 기기 백업에서 빼고, 기기를 바꿀 때 쓰도록 R1에 데이터 내보내기·가져오기(파일, 쿠키·토큰 제외)를 더한다.
  - 사캠 연결: 폰 직접 연결은 R1로 미루고, 확장은 사용자가 PC에서 사캠을 쓸 때만 조회한다(2026-10-11 '사캠 연동 방식', 'PC 브라우저 확장').
  - 배치: 처음 명세처럼 할 일을 자동으로 배치하되 사용자가 확정하고, 블록마다 근거를 보여 준다(2026-10-12 '하루 루프와 배치 엔진').
  - 개인화: 처음 명세의 '자연어로 설정 변경'을 '내 규칙'으로 R0에 넣는다(아래 항목).
  - 화면: 캘린더 탭을 R0부터 두고 R0에 일간·월간, R1에 주간(새 디자인)을 더한다. 홈은 오늘 일정 중심 그대로이고 브리핑은 별도 화면이다.
  - 브리핑과 알림: R0 브리핑에 '어제 못 한 일' 카드를 두고 미완료마다 따로 알림을 보내지 않는다(R1 저녁 체크인은 그대로). 주간 요약은 R1에 월요일 아침 브리핑 카드로 붙인다(지난주 확정 블록 완료율, 지난주 마감 사캠 항목 가운데 제출·출석을 마친 수, 다음 주 마감 수와 남은 예상 작업 시간). 알림의 '완료'·'미루기' 버튼과 알림 반응 기록은 R1, 반응 기록으로 알림 시점·빈도를 스스로 바꾸는 자동 조정은 R2다. 그전에는 사용자가 '내 규칙'으로 브리핑 시각·하루 알림 상한·조용한 시간을 바꾼다.
  - 넣지 않는 것: 사캠 과목 공지는 모으지 않고 사캠 페이지로 연결만 한다. Android 알림 감지는 R1 그대로다.
- 이유: 폰 중심 구조는 같은 입력에 같은 계획을 내고, 오프라인에서도 계획과 알림이 돌며, 서버에 읽을 수 있는 개인 데이터를 두지 않는다. 개인화도 폰에서 할 수 있어 서버 agent가 필요하지 않다. 기기 백업에서 빼는 것은 사캠 데이터와 일정이 클라우드 백업에 남지 않게 하기 위해서이고, 기기를 바꾸면 데이터가 자동으로 따라가지 않는 것은 감수한다(R1의 데이터 내보내기·가져오기로 옮긴다). 하루 루프에 바로 닿는 기능(자동 배치, 못 한 일, 캘린더로 블록 보기, 내 규칙)은 R0에 넣고 나머지는 R1·R2로 둬 R0 범위를 지킨다. 미완료마다 알림을 보내면 하루 알림 상한을 빨리 쓰고 못 한 일을 탓하는 느낌을 준다. 공지는 과목마다 형식이 달라 해석 비용이 크고 사캠에서 보는 편이 정확하다.
- 다른 후보: 서버 agent가 사용자 데이터를 저장하고 계획·알림을 만들기(계정과 서버 DB가 필요하고 개인정보 책임이 커지며 알림이 서버와 네트워크에 기댐), 폰 DB를 기기 백업에 넣기(기기를 바꿔도 이어지지만 사캠 데이터가 클라우드 백업에 남음), 캘린더를 R1로(R0에 블록을 날짜별로 볼 곳이 없음), 미완료마다 저녁 알림(알림이 늘어남), 주간 요약을 따로 알림으로(알림이 늘어남), 공지 요약(해석 부담이 크고 사캠 화면과 어긋날 수 있음).

## 2026-10-13 내 규칙

- 결정: 사용자가 배치 조건을 말로 알려 주면(예: "학교에서 집까지 한 시간 걸려") `/v1/parse`가 정해진 규칙 종류 가운데 하나의 JSON(`intent` `set_rule`)으로 바꾸고, 앱이 바꿀 내용을 코드가 만든 문장으로 보여 준 뒤 승인을 받으면 폰 DB `rules`에 저장하고 배치를 바로 다시 계산한다. 규칙 종류는 이동 시간, 수업 앞뒤 여유, 공부 가능한 시간대, 피할 시간, 선호 시간대, 한 번에 할 최대 시간, 하루 최대 공부량, 식사, 예상 시간, 알림(브리핑 시각·하루 상한·조용한 시간) 열 가지이고 표는 [architecture.md](architecture.md)에 있다. 애매하면 되묻고(위 예는 매 수업 앞뒤인지, 하루 첫 수업 전과 마지막 수업 뒤인지), 종류에 없는 조건과 범위를 벗어난 값은 저장하지 않는다. 확정 블록이 새 규칙과 겹치면 블록마다 옮길지 묻는다. 규칙은 나 탭의 '내 규칙'에서 켜고 끄고 고치고 지우며, AI에 동의하지 않은 사용자는 같은 규칙을 폼으로 정한다. 서버는 규칙을 저장하지 않는다. R0에 넣는다. 행동에서 배우는 조정(실제 걸린 시간으로 예상 시간 고치기, 자주 지운 제안을 보고 선호 시간대 묻기)은 R1이고 늘 사용자에게 물은 뒤 저장한다. 평가 세트에 규칙 문장을 넣고 규칙 정확도 95% 이상을 맞춘 뒤 연다.
- 이유: 통학 시간, 일하는 시간, 공부 습관이 사람마다 달라 기본값 하나로는 맞는 계획을 낼 수 없다. 말로 정하면 설정 화면을 찾지 않아도 된다. LLM은 문장을 닫힌 형식으로 바꾸기만 하고 적용은 폰의 결정적 코드가 하므로, 같은 규칙이면 같은 계획이 나오고 잘못 해석해도 저장 전 미리보기에서 걸러진다. 규칙이 폰에만 있어 폰 중심 구조와 개인정보 원칙을 그대로 지킨다.
- 다른 후보: 서버 agent가 사용자별 설정을 저장하고 계획에 반영(서버에 개인 데이터가 쌓이고 계정이 필요함), 자유 형식 규칙을 LLM이 매번 해석해 배치(결정적이지 않고 호출 비용이 듦), 폼 설정만(처음 명세의 자연어 설정 변경을 잃음), 행동에서 배워 묻지 않고 바꾸기(사용자가 모르는 사이 계획이 바뀜).

## 2026-10-26 사캠 연동 방식 재정의 (2026-10-11 결정 뒤집음)

- 결정: 2026-10-11 '사캠 연동 방식'·'PC 브라우저 확장'과 2026-10-11 '출시 단계'의 사캠 부분을 뒤집는다. 새 방식은 이렇다.
  - **폰 직접 연결이 유일한 연결 방식이고 R0다.** PC 브라우저 확장과 중계 서버(암호문 중계, 확장 설정 전달)는 R0·R1에서 모두 없앤다. `extension/`, `functions/src/relay/`, QR 페어링, 관련 Firestore 컬렉션, 실험 T13, `settings`의 `pcPairId`·`pcLastReceivedAt`·`lmsPhoneFallback`과 `lmsMode`의 `pc` 값을 뺀다.
  - **앱이 비밀번호를 OS 보안 저장소에 저장하고, 세션이 끊기면 조용히 다시 로그인한다.** 처음 로그인은 사용자가 앱 안 WebView의 공식 화면에서 하고, 그때 입력한 비밀번호를 사용자가 '자동 로그인 유지'를 켜면 보안 저장소에 저장한다. 끄면 저장하지 않고 끊길 때마다 다시 로그인 화면을 띄운다. 비밀번호는 기기 밖(서버 포함)으로 나가지 않는다.
  - **시간표를 자동으로 불러온다(R0).** 사캠에는 요일·교시가 없고 학교 통합정보시스템에서 받는다. 온보딩·시간표 화면에서 과목을 고르면 요일·시각·강의실이 자동으로 채워지고, 사용자가 확인·수정한다. 자동으로 못 채운 과목(온라인 등)은 직접 입력한다. R2의 '시간표 캡처(OCR)'는 뺀다.
  - **연결 약속은 "앱을 열면 최신"이다.** 앱을 열 때, 쓰는 동안 주기적으로, 그리고 OS가 백그라운드로 깨워 줄 때(R1) 조회한다. 세션이 끊겨 있으면 저장된 비밀번호로 먼저 다시 로그인한다.
- 사실 정정(이전 문서가 틀렸던 것): 포털 로그인은 비밀번호를 평문으로 보낸다(HTTPS). RSA 암호화는 LMS 자체 로그인에만 쓴다(2026-10-11 문서와 반대). "저장된 자격증명으로 조용히 다시 로그인하는 길이 없다"는 틀렸다. 가능하고, 다만 그때마다 계정의 다른 기기(PC·웹) 세션이 끊긴다(계정당 세션 하나). 사캠 할 일 목록 응답에는 영상 길이·인정 시간·시청 시간·제출 여부가 없고, 과목별 강의실 상세 조회에서 받을 것으로 보이나 아직 확인하지 않았다.
- 이유: 사용자가 로그인 → 세션 유지 → 할 일·공지·시간표 조회와 자동 재로그인까지 도는 프로토타입을 직접 만들어 확인했다. 확장을 둔 까닭은 둘이었다. 앱이 비밀번호를 다루지 않게 하려는 것과, 자동 로그인이 PC 영상강의 세션을 끊는 것을 피하려는 것이다. 사용자가 두 번째를 감수하기로 하면서, 연결 경로를 하나로 줄이고 중계 서버·확장·QR·브라우저 배포를 만들지 않는 쪽이 전체 비용이 작다. 시간표 자동 불러오기가 되면 온보딩에서 손으로 넣는 부담과 R2 OCR이 필요 없다.
- 받아들인 대가: ① 앱이 학교 비밀번호의 보관 책임자가 된다(서버가 아니라 기기 보안 저장소). 온보딩 문구, AI 동의와 별개인 개인정보 처리방침, 스토어 Data Safety·App Privacy가 바뀐다. ② 앱이 로그인·재로그인할 때마다 PC나 웹의 사캠 세션이 끊긴다(서버 정책, 피할 수 없음). 원래 확장이 지키려던 'PC 영상강의 세션'은 더 이상 지켜지지 않는다. ③ 폰 세션 관리(WebView 로그인, 쿠키 금고, 세션 복원, 통합정보시스템 핸드셰이크)가 R0의 핵심이 된다. iOS 백그라운드 제약 때문에 약속은 "앱을 열면 최신" 수준이 현실적이다.
- 공개 레포 원칙은 그대로다. 사캠·통합정보시스템의 엔드포인트, 요청 상수, 암호화 키·방식, 판별 표식, 쿠키 이름, 실제 응답은 레포에 적지 않고 Remote Config로 받는다. 비밀번호 저장·자동 재로그인·세션·시간표 조회의 구체 방식은 `docs/lms.md`에 동작 규칙으로만 적는다.
- 다른 후보: 확장 기본 유지(2026-10-11 결정. 중계 서버·확장·브라우저 배포를 만들어야 하고 PC에서 사캠을 안 여는 날은 갱신이 멈춤), 비밀번호를 저장하지 않고 끊길 때마다 수동 로그인(끊김이 잦으면 로그인 화면을 자주 봄. 자동 로그인을 끈 사용자에게는 이 방식), 시간표를 계속 손으로만 입력하고 자동 불러오기를 빼기(통합정보시스템 조회를 안 해도 되지만 온보딩 부담이 큼), 서버 대리 로그인(서버에 비밀번호·세션이 모여 유출 책임이 커지고 한 IP에서 많은 계정이 접속해 학교가 막을 위험).

## 2026-10-31 할 일 배치는 사용자가 직접 (2026-10-12 '하루 루프와 배치 엔진', 2026-10-13 '처음 기능 명세와 맞추기'의 배치 부분 뒤집음)

- 결정: 배치 엔진이 할 일을 빈 시간에 자동으로 넣어 제안 블록을 만드는 기능을 없앤다. 앱은 시간이 정해지지 않은 할 일을 '미배정 할 일' 목록으로 보여 주고, 사용자가 할 일마다 '배치'를 눌러 말("내일 오후 2시부터 2시간")이나 직접 입력으로 시간을 정한다. 말은 지금처럼 `/v1/parse`가 해석하고, 제목은 그 할 일 이름, 길이를 말하지 않으면 남은 작업 시간만큼 잡는다. 정한 블록은 바로 확정(`confirmed`)이다. 입력하는 동안 겹치는 일정은 경고만 하고, 마감 뒤로 잡으면 저장하지 않는다.
- 남기는 계산: 빈 시간 계산(`domain/free_slots.dart`)과 여유도(마감 전 빈 시간 합 − 남은 작업 시간)는 그대로 쓴다. 여유도는 미배정 목록의 순서(작은 것부터)와 '높음·보통·낮음' 표시, 여유도가 0 아래인 할 일의 '시간 부족' 경고에, 빈 시간은 실시간 시간표의 '남은 빈 시간'과 배치 시트의 기본 시각에 쓴다. 등급 경계는 `domain/defaults.dart`의 임시값이다.
- 없애는 것: `planRange`·`suggestSlots`, 제안 블록(`suggested`)과 지운 제안(`dismissed`), 블록 근거(`reason`)와 근거 시트, 브리핑의 '모두 확정', 놓친 블록의 자동 재배치. 놓친 확정 블록은 그대로 `missed`로 두고 다시 미배정 목록에 올린다.
- 이유: 자동 제안은 사용자가 모르는 계산 결과를 매번 확인·확정해야 하고, 학생의 하루(알바·약속·이동)는 앱이 아는 것보다 변수가 많다. 사용자가 직접 시간을 정하고 앱은 '무엇이 급한지'와 '언제 비는지'를 보여 주는 쪽이 이번 기획 검토에서 더 잘 맞았다.
- 받아들인 대가: 하루 루프의 자동화가 줄어든다. '내 규칙' 가운데 배치에만 쓰던 종류(`preferred`, `max_block`, `daily_cap`)는 쓸 곳이 줄어들며, 남길지는 코드 PR 전에 새 항목으로 정한다. 지표의 '오늘 제안 있음'·'계획 확정'도 다시 정해야 한다.
- 다른 후보: 기본은 직접 배치하고 '제안 받기' 버튼으로 엔진 제안을 보조로 두기(엔진 코드와 근거 화면을 계속 유지해야 함), 기존 결정 유지(위 이유).

## 2026-10-31 데일리 브리핑 범위와 중요 브리핑

- 결정: 아침 브리핑은 이름을 '데일리 브리핑'으로 쓰고, 사용자가 정한 시각(`notify` 규칙. 기본값은 지금처럼 임시값)에 직전 마지막 접속 시각부터 그 시각까지 생긴 일을 요약한다. 순서는 글 브리핑(AI 문장, 실패하면 템플릿) → 날씨 한 줄(R1) → 오늘 일정 → 미배정 할 일 → 마지막 접속 이후 변경 사항이고, 상단(제목·닫기)은 스크롤해도 고정한다. 그날 처음 앱을 열 때 한 번 보여 주고, 그 뒤 앱을 열면 캘린더가 첫 화면이다.
- 결정: 새로 '중요 브리핑'을 둔다. 하단 원형 버튼을 누르면 시트로 열리고, 브리핑 시각 이후 지금까지의 상황(끝난 일정, 남은 일정, 새로 생긴 일, 오늘 챙길 할 일)을 글로 알려 준다. 긴급 알림이 아직 안 본 것이 있으면 버튼에 레드닷을 단다. 시트가 열리면 버튼은 같은 자리에서 닫기(X)가 되고, 손잡이·제목을 아래로 끌어도 닫힌다. 제목 오른쪽에 알림함·데일리 브리핑 보기 버튼을 둔다. 일정 배치는 하지 않는다.
- 단계: R0의 중요 알림은 사캠 새 항목·마감 변경과 오늘 일정 변경이다. R1에 재난문자(서버가 공개 데이터로 받고, 폰은 사용자가 고른 시·군·구만 요청하며 위치 좌표는 보내지 않음)와 Android 알림 감지를 더한다. 알림 감지는 2026-10-13 결정대로 R1이고, 알림 원문은 폰 DB에만 두며 AI 요약이 필요하면 지금처럼 게이트웨이로 제목을 가려 보낸다.
- 이유: 아침에는 밤사이 쌓인 것을 한 번에 보고, 낮에는 바뀐 것만 따로 보면 같은 내용을 두 번 읽지 않는다. 레드닷은 확인할 것이 있을 때만 사용자를 부른다.
- 다른 후보: 데일리 브리핑 범위를 '최근 24시간'으로 고정(전날 밤 늦게 본 것을 다시 보여 줌), 중요 알림을 모두 푸시 알림으로(하루 알림 상한을 빨리 씀).
