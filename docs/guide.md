# 팀원 가이드

이 레포에서 작업하는 흐름을 정리했습니다. 정확한 규칙은 [CLAUDE.md](../CLAUDE.md)에 있고, Claude Code는 작업할 때마다 그 파일을 읽고 규칙대로 움직입니다. 이 문서는 사람이 알아 두면 좋은 흐름과 요령입니다.

## 전체 흐름

```
develop ──●──────────●──────────●──────────▶   (모두의 작업이 모이는 곳)
           \        /  \        /       \
            feat/login   fix/crash       \      (내 작업 브랜치)
                                          ▼
main    ───────────────────────────────────●──▶ (발표·제출 때만)
```

1. develop에서 내 작업 브랜치를 만듭니다.
2. 브랜치에서 코드를 고치고 커밋합니다.
3. GitHub에 올리고 develop으로 PR을 보냅니다.
4. 검사(`pr-rules`)가 통과하고 리뷰어로 지정한 팀원 1명이 승인하면, 내가 직접 **Squash and merge**를 누릅니다.
5. 발표나 제출 때는 develop을 main으로 올립니다. 이때는 팀원 1명이 승인해야 합니다.

main과 develop에 직접 push하면 GitHub가 거부하므로, 잘못 push해도 두 브랜치는 망가지지 않습니다.

## 처음 한 번만

1. 메일이나 GitHub 알림으로 온 레포 초대를 수락합니다.
2. Git과 GitHub CLI(gh)를 설치합니다. 방법을 모르면 Claude Code에게 "git이랑 gh 설치 도와줘"라고 하면 됩니다. 설치한 뒤에는 터미널과 Claude Code를 닫았다가 새로 열고, 아래 명령을 직접 입력해 로그인합니다. 질문이 나오면 엔터로 기본값을 고르면 됩니다.
   ```bash
   gh auth login
   ```
3. 레포를 내려받습니다.
   ```bash
   gh repo clone syujin2323/cnu-ai-assistant
   cd cnu-ai-assistant
   ```
4. **Claude Code는 꼭 이 레포 폴더에서 실행합니다.** 다른 폴더에서 열면 CLAUDE.md를 읽지 못해 규칙을 모릅니다.

## 작업 한 바퀴: Claude에게 이렇게 말하세요

| 하고 싶은 것 | Claude에게 | Claude가 하는 일 |
|---|---|---|
| 새 작업 시작 | "로그인 화면 만들 거야. 브랜치 만들어줘" | develop을 최신으로 받고 `feat/login-screen` 같은 브랜치를 만듭니다 |
| 코딩 | 평소처럼 요청 | |
| 저장 | "지금까지 한 거 커밋해줘" | `feat: 로그인 화면 추가` 같은 형식으로 커밋합니다 |
| 올리기 | "PR 올려줘" | 제목과 본문을 먼저 보여 주고 리뷰어를 물어봅니다. 확인하면 push하고 PR을 만듭니다 |
| 합치기 | "승인 받았으면 병합해줘" | 승인을 확인하고 develop에 squash로 병합한 뒤, develop으로 돌아와 작업 브랜치를 정리합니다 |
| 다음 작업 준비 | "develop 최신으로 받아줘" | develop으로 돌아가 최신 내용을 받습니다 |

Claude가 제목이나 본문을 보여 주면 그냥 넘기지 말고 한 번 읽어 보세요. 그 PR이 팀의 기록으로 남습니다.

## 커밋 메시지와 PR 제목

형식은 `종류: 설명` 하나뿐입니다. 설명은 한국어든 영어든 괜찮습니다.

| 종류 | 언제 | 예 |
|---|---|---|
| `feat` | 새 기능 | `feat: 로그인 화면 추가` |
| `fix` | 버그 수정 | `fix: 빈 목록에서 앱이 꺼지는 문제` |
| `docs` | 문서만 바꿈 | `docs: 실행 방법 정리` |
| `refactor` | 동작은 그대로, 코드만 정리 | `refactor: 네트워크 코드 분리` |
| `test` | 테스트 | `test: 로그인 실패 경우 추가` |
| `chore` | 설정, 라이브러리, 포맷 등 그 밖의 것 | `chore: Gradle 버전 올림` |
| `release` | develop → main PR 전용 | `release: 중간 발표 버전` |

PR 제목은 develop에 그대로 남는 기록이라 GitHub가 검사합니다. 브랜치 안에서 하는 커밋은 검사하지 않지만, 같은 형식으로 쓰는 습관을 들이면 좋습니다.

## PR 본문

PR을 만들면 본문에 틀이 미리 들어갑니다. Claude에게 맡기면 Claude가 채워 줍니다.

- **무엇을, 왜**: 코드만 봐서는 모르는 이유를 적습니다. 다음 사람(과 다음 사람의 Claude)이 이걸 읽습니다.
- **확인한 방법**: 실제로 실행해 본 것을 적습니다. "AI가 짰으니 될 것"은 확인이 아닙니다.
- **스크린샷**: 화면이 바뀌었을 때 붙입니다.
- **체크**: Claude는 비워 둡니다. 내가 직접 확인하고 GitHub PR 페이지에서 눌러 체크합니다.

## Claude와 컨텍스트 유지하기

Claude는 대화가 끝나면 내용을 잊습니다. 다른 팀원의 Claude는 내 대화를 아예 볼 수 없습니다. 그래서 남겨야 할 것은 레포 안에 적어 둡니다.

| 무엇을 | 어디에 | 누가 읽나 |
|---|---|---|
| 팀 규칙 | `CLAUDE.md` | 모든 Claude가 세션을 시작할 때마다 자동으로 읽음 |
| 폴더 구조, 실행 방법, 앱-서버 API | `docs/architecture.md` | CLAUDE.md가 불러와서 자동으로 읽음 |
| 팀이 정한 것과 이유 | `docs/decisions.md` | CLAUDE.md가 불러와서 자동으로 읽음 |
| 이번 작업에서 한 일과 이유 | PR 본문 | 리뷰하는 사람, 나중에 기록을 찾는 사람 |

요령은 이렇습니다.

- **회의에서 정한 게 있으면** Claude에게 "방금 정한 거 decisions.md에 남겨줘"라고 하고 PR로 올립니다. 그래야 다른 팀원의 Claude도 압니다.
- **어제 하던 작업을 이어서 할 때**는 레포 폴더에서 `claude --continue`로 지난 대화를 이어 엽니다. 새로 열었다면 "이 브랜치에서 지금까지 한 일 보고 이어서 하자"라고 하면 Claude가 커밋 기록을 읽고 파악합니다. 그 브랜치가 이미 병합됐으면 Claude가 알려 주고 새 브랜치를 만듭니다.
- **다른 작업으로 넘어갈 때**는 `/clear`로 대화를 비웁니다. 앞 작업 내용이 섞이면 Claude가 헷갈립니다.
- **큰 기능은 계획부터** 세웁니다. `/plan 로그인 기능 계획 세워줘`처럼 앞에 `/plan`을 붙이면 코드를 고치기 전에 계획을 먼저 보여 줍니다.
- **CLAUDE.md는 혼자 고치지 않습니다.** 규칙을 바꾸고 싶으면 팀에 먼저 말하고 PR로 올립니다. Claude가 같은 실수를 두 번 이상 하면 그때 규칙을 추가하자고 제안해 주세요.

## 리뷰와 병합

- **develop으로 가는 PR**: GitHub는 승인 없이도 병합을 허용하지만, 팀 약속으로 리뷰어 1명을 지정하고 승인을 받은 뒤 병합합니다. 리뷰어는 PR 페이지 오른쪽 **Reviewers**에서 지정합니다(Claude에게 맡기면 PR을 만들 때 지정해 줍니다). 검사(`pr-rules`)가 초록색이고 승인을 받으면 작성자가 직접 **Squash and merge**를 누릅니다(버튼 이름이 다르면 옆 ▼에서 고릅니다).
- **main으로 가는 PR**: 발표나 제출 전에 만듭니다. 작성자가 아닌 팀원 1명이 **Approve**해야 병합됩니다. 병합 방식은 **Create a merge commit**입니다.
- 리뷰를 부탁받으면 PR 페이지의 **Files changed** 탭에서 바뀐 코드를 보고, 괜찮으면 **Review changes → Approve → Submit review**를 누릅니다.

## 막혔을 때

| 증상 | 이유 | 해결 |
|---|---|---|
| push하면 `GH013` / `repository rule violations` 오류 | main이나 develop에 직접 push하려 함 | Claude에게 "방금 커밋을 새 브랜치로 옮겨줘" |
| PR에 `pr-rules` 빨간 X | 제목 형식이 틀렸거나, 작업 브랜치에서 main으로 PR을 보냄 | PR 제목 옆 **Edit**에서 제목이나 대상 브랜치(base)를 고치면 자동으로 다시 검사. Claude에게 "PR 검사 실패한 거 고쳐줘"라고 해도 됨 |
| PR에 `This branch has conflicts` | 다른 사람이 같은 곳을 먼저 고침 | Claude에게 "develop 최신 내용 받아서 충돌 해결해줘" |
| Merge 버튼이 회색 | 검사 실패, 충돌, 또는 승인 필요(main) | PR 페이지 아래쪽 안내 문구를 확인 |
| API 키나 `.env`를 올림 | | 바로 팀에 알리고 그 키를 발급한 곳에서 폐기. 지우는 것보다 폐기가 먼저 |

그래도 모르겠으면 Claude에게 화면에 나온 오류를 그대로 붙여 넣고 "이거 무슨 뜻이야?"라고 물어보세요.
